# 项目代码风格与编程约束

让新增代码自然融入项目，以需求、契约和可验证的失败路径决定复杂度。遵循适用的上级指令和用户明确选择；本 Skill 不扩大任务范围，也不要求每次修改都生成文档、执行全库扫描或增加测试。

从当前项目及其适用规则取得语言、格式、分层和接口约定。用户指定参考项目时，只沿用本次要求继承的部分。各参考文档的示例用于说明核对方法，项目没有对应能力时可跳过。

## 先确定本次产物

| 用户目标 | 工作范围 |
| --- | --- |
| 学习项目、梳理架构或风格 | 按 [项目分析与证据](references/project-analysis.md) 分析，交付有证据的认识与未知；不隐含修改业务代码 |
| 新增、修复或重构代码 | 分析受影响模块，执行下述编程约束；普通局部修改不加载全项目分析流程 |
| 审查代码 | 沿真实调用链检查改动、兼容性和失败结果，按影响报告有证据的发现；仅审查时保持文件原样 |
| 明确要求提炼框架或迁移 | 结合 [项目分析与证据](references/project-analysis.md) 和 [架构提炼与验收](references/architecture-extraction.md)，在相关认识足够后实现 |
| 对照参考项目审查已有实现 | 按 [双向源码对照](references/project-analysis.md#双向源码对照) 审查。需要核对函数、结构体或排版时，读取 [定义与使用风格复原](references/style-contracts.md) |

用户提供项目来评估或改进 Skill 时，产物是 Skill 及其验证记录。参考项目只读。用户要求对照审查时，按源码列出差异和影响。用户要求实际改码验证时，在指定样本完成代表性改动并验证，也可按需在工作区测试目录实现小样本。

用户以“能复原原项目的结构、定义与使用方式”检验学习效果时，使用 [定义与使用风格复原](references/style-contracts.md)。分析和比对能确定约束，实际改码才能验证这些约束能否指导实现。把原样复原的契约和现有样本必须保持的行为分别验收。

## 先学习所在模块

- 先读适用的 `AGENTS.md`、相关格式与静态检查配置、依赖清单及现有测试命令。只查看本次工作需要的配置。
- 学习或修改应用配置文件时，按 [配置文件风格与契约](references/project-analysis.md#配置文件风格与契约) 对照同模块的文件和实际加载器，分别核对人工编辑习惯和运行契约。
- 沿目标代码的调用链，选取足以判断惯例的相邻实现、调用方和测试。关注命名、目录与分层、类型、错误表示、异步与资源生命周期、日志、依赖注入和测试写法；不凭一份文件推断全仓库风格。
- 学习结果应能落到实际符号：结构体/类的字段与类型、函数完整签名、声明和定义文件、调用参数及资源使用方式。生成需要沿用这些符号的代码前，先将原定义和使用链作为约束，再检查产物是否满足；未映射的新接口不得算作已复原。对已有定义的复原不得仅保留名字后重写字段、接口或位置；具体核对方式按需读取 [定义与使用风格复原](references/style-contracts.md)。
- 已有风格档案存在时，只读取相关部分，并核对源码是否仍支持它。显式项目规范优先于偶然写法；模块内稳定惯例优先于其他模块的多数写法。配置、文档、代码相互冲突时，说明冲突并选择有证据且符合当前需求的方案；只有影响外部契约等关键选择时才询问用户。
- 新增辅助函数、包装器或重复一段已有职责前，先从同类调用点找现有入口，再沿相关模块和公共接口按职责、类型或副作用检索。核对输入输出、失败行为、状态与依赖边界。能直接复用就调用，适合在原所有者扩展就检查消费者后扩展，简单操作沿用局部写法。只有现有路径无法满足当前需求时才增加最小实现，重要新增在审查时说明所查入口和具体缺口。见 [复用与辅助函数](references/code-decisions.md#9-复用与辅助函数)。
- 每次扩展阅读范围前，明确要解决的疑点及其对当前决定的影响。对于已授权的代码修改，能从局部契约解释改动、消费者与验证方法时即可实施；无关模块保持未知，不为“学习充分”扫描整个仓库。
- 在需要修改代码的任务中，修正正在影响任务的缺陷；不要照搬漏洞、错误契约或已弃用接口来追求一致。新项目缺少惯例时，采用现有工具链的简单常规写法，不虚构已有风格。

需要持久化学习成果时，参考 [风格档案模板](assets/project-style-template.md)，复用项目既有文档；没有既有位置时可使用 `docs/coding-style.md`。若项目只是只读参考，结果写在当前交付位置，不向参考项目写文档或规则。区分“明确规范、观察到的惯例、建议”，附源码位置或符号作为证据；不把推断写成强制规范，不把分析建议自动写进 AGENTS。普通小改动无需新建档案。

## 按证据编程

- 只实现当前需求及其必需改动。新增抽象、配置开关、缓存、兼容层、重试或依赖，应有当前调用需求、明确契约或已观察到的故障依据。复杂度以能清楚解释当前职责为准，不设行数或抽象层数指标。
- **先确定防护边界，再决定校验。** 外部请求、文件、环境变量、数据库历史数据、第三方返回值和公共 API 参数按契约校验；静态类型不是运行时外部数据校验。内部已验证的数据按可信契约使用，除非后续可变性或新的信任边界使原保证失效。
- 不因“可能出问题”逐层重复判空、猜测字段别名、放宽类型、强制类型转换或添加永远无法到达的分支。先查看类型、入口校验、生产者与调用方，证据不足时调查，不直接删检查。
- 审查疑似过度防御时，说明检查防止的失败、数据由谁保证、删改会改变什么行为。边界校验、业务状态校验、资源获取检查及并发复核不因形式重复而自动多余；入口快筛与锁内复核可能承担不同职责。没有证据时保留并标注待核实，不为了减少检查数量改代码。
- 不用空集合、零值、假对象、成功状态或过宽的 `catch` 隐藏真实失败。允许产品契约明确的降级、批处理的逐项失败隔离和容错，但要保留项目规定的可观察性与失败语义。
- 网络和存储等真实故障按项目机制处理。重试仅针对可重试错误，并考虑次数、取消、超时和副作用幂等性；不在普通函数中自行叠加全套机制。
- 修复从失败输入、调用链和可重复证据出发。跨层故障先找实际结果首次偏离契约的位置，再选能区分原因的检查。无法复现时使用日志、静态分析等现有证据，并明确验证限制。
- 新增 API 或依赖先核对项目锁定版本、声明文件或官方文档；包存在不代表可信，不因模型建议的名字直接安装。优先项目已有依赖或标准库，不顺手升级无关依赖。
- 涉及状态机、并发或资源池时，先明确状态由谁修改、哪把锁保护、资源何时归还和何时失效。区分非法输入、业务拒绝、暂时故障与内部错误，确定它们应返回错误、断连还是使进程失败；不要让宽泛异常捕获偶然决定对外行为。

遇到防御代码、异常语义、重试或抽象取舍不明确时，按需阅读 [代码示例与取舍](references/code-decisions.md)。

## 收敛修改并验证行为

- 保持当前需求之外的格式、命名、注释和接口稳定。清理由本次改动造成的未使用项；无关历史问题单独说明。
- 排版与结构契约分别检查：编译通过和 formatter 通过都不能证明复原准确。以参考定义、文件归属和实际调用对照；格式配置若与局部源码惯例不一致，不把通用预设冒充为已学到的项目风格。
- 按适用规则和同类源码判断续行。项目偏好单行调用或声明时，避免因默认列宽或参数逐个排版而拆开完整语句。多个独立语句与控制块仍各自排版。
- 改公共接口、持久化结构或错误语义时，检查实际消费者及迁移影响。必要的兼容不应被“简化”误删；不为猜想中的未来消费者加兼容。
- 以用户需求和既有契约确定验收标准。优先已有格式检查、类型检查和相关测试；缺陷修复通常补充能暴露原缺陷的行为回归测试。简单文案或低影响改动采用相应检查即可，不机械要求测试先行或全量测试。
- 测试检查外部可观察结果、重要失败路径与副作用；不靠删断言、放宽类型、关闭检查、过度 mock 或改写需求让测试通过。只有契约确实改变时才更新断言并说明原因。
- 最终核对本次差异和实际调用方。移除被排除的假设留下的分支、包装、临时日志或测试改动，保留用户已有修改。若继续整理没有可说明的收益，停止修改。
- 验证前确认命令使用的源码、构建产物、配置与替身范围，并覆盖实际入口或生产调用的同一实现。源码、配置或依赖变化后重跑受影响的检查。分别报告构建、运行与行为证据。复杂情况见 [排查与验证取舍](references/code-decisions.md#10-排查与验证取舍)。
- 最终简述改了什么、沿用了哪些关键惯例、实际验证结果及尚未验证的部分。不要声称未运行的检查已通过。

## 让后续约束持续可用

将用户确认、反复适用的项目规则放在该项目的 `AGENTS.md`，让核心规则在 Skill 未触发时也可读。将源码观察、例外和符号位置留在风格档案。合并时保留原有规则和目录作用域，见 [AGENTS.md 合并片段](assets/agents-snippet.md)。

长任务需要跨会话或可能丢失上下文时，复用已有计划或交接文件，记录当前目标、用户确认的任务约束、已完成与已验证的范围、未决项和下一步。只有有实际续接需求时才维护记录。新会话从正确的项目目录开始。恢复或接手后，重新核对适用规则、任务记录和当前工作树，再继续最近未完成的步骤。用户的新指令优先于旧任务记录，任务临时决定不能自动升级为项目规则。

学习和约束不是模型训练，也不是强制执行器。重要且可机械检查的规则，优先使用项目已有 formatter、linter、类型检查和 CI；新增或收紧这些配置应属于当前授权范围。
