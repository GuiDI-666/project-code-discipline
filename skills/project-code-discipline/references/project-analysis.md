# 项目分析与证据

适用于用户明确要求学习整个项目，以及作为框架提炼、迁移的前置分析。分析的目标是还原项目实际如何组织和运行，不能以“我会怎样设计”替代“源码现在怎样工作”。

先明确本次要回答什么、产物是什么以及项目是修改对象还是参考材料。“学习”“审查”“评估 Skill”本身不意味着实现新框架。输出深度由问题决定，不固定要求一套完整架构文档。

## 先定范围与分析依据

- 确认项目边界、适用规则、构建入口、参与构建的源码、依赖与生成代码。排除无关备份和第三方实现，除非它们是当前调用链所需。
- 文件名和目录只用来提出假设。核对构建清单、符号、调用方与实际实现后再描述职责；头文件也可能包含实现，代码可能包含 `.cpp`，同名服务未必是独立进程。
- 识别生成的产物是否对应当前源码。现有可执行文件或历史构建通过不证明当前源码可用。不以文件数量、阅读行数或搜索命中数作为“分析完成”的证据。

## 从问题追踪到足够证据

采用“当前问题 → 找到定义与调用方 → 核对条件/数据 → 修正判断”的方式推进。先从构建/入口和目标功能定位，再沿关键调用与数据流扩展；不要从目录树推导完一套分层后再寻找支持材料。

关键判断应主动找可能推翻它的分支或调用者。例如，判断“某服务已启动”时查启动调用与开关；判断“检查多余”时查未经过入口校验的调用方；判断“某写法是规范”时查适用配置和同模块其他实现。反证检索仅围绕影响当前判断的部分，不扩成全面审计。

## 按关键链路还原项目

围绕实际存在的职责逐层追踪；缺少对应职责就说明不适用，不替项目虚构模块。

1. **生命周期**：模块导入/静态初始化、入口、配置、外部资源、后台工作、停止与清理。不要假定所有初始化都从 `main` 开始。
2. **功能闭环**：从实际触发点追到可观察结果和副作用。服务端可追请求到响应，前端可追事件到状态与渲染，命令行可追参数到处理与输出；核对关键调用边，而非只列函数名。
3. **状态与数据**：核心结构的创建者、持有者、读写方与销毁者；追踪关键值的来源、类型转换、参数传递和实际使用，不能只归纳职责名称。数据校验、状态切换、异步和持久化在哪里发生。仅对实际并发部分调查线程与锁。需要复原时按 [定义与使用风格复原](style-contracts.md) 核对指针、长度、分发和所有权细节。
4. **横向能力**：按下文“运行能力与业务分布”核对关键运行支撑与各自入口。区分构建期、部署期与运行期条件。
5. **失败闭环**：输入失败、业务拒绝、外部故障和部分初始化失败如何传播、转译或退出。不要把日志存在当成错误已妥善处理。

分析有状态函数时，核对调用前提、正常结果、失败后的状态和已经发生的副作用。返回 `false` 可能意味着保留旧状态、恢复默认值或留下部分更新，必须沿赋值与提交位置确认；不能仅凭返回值、异常类型或日志判断。涉及多个编译单元、插件或异步任务的初始化顺序时，区分源码可见顺序与框架/运行时实际保证，不把局部文本顺序扩展为全局顺序。

对影响结论或实现的判断记录“结论 → 源码符号/配置 → 条件与范围 → 已确认/推断/待核实”。仅对实际执行过的行为标记运行验证。不要求记录每个函数；静态分析任务无需为了填表启动服务或修改数据。

## 运行能力与业务分布

用于整项目学习、框架范围核对，或用户专门要求核对下列能力。对于局部改动，只查与问题有关的行。入口可能藏在静态构造、回调、控制台命令、定时器、头文件实现或平台注册中。

按项目形态选取能力。桌面应用、批处理、库和服务端的入口与运行支撑各不相同。对没有独立配置、后台任务或诊断机制的项目，记录不适用即可。

| 核对项 | 追踪到可判断的结果 |
| --- | --- |
| 崩溃和错误处理 | 从实际注册或外层捕获找到处理函数，区分进程崩溃、应用异常、业务拒绝和正常关闭。核对错误信息、转储/报告的去向、依赖缺失与调试分支、是否检查写入结果及之后继续或退出。仅定义了 handler 不算启用。 |
| 日志和控制台 | 核对初始化先后、实际 logger 和 sink、级别、轮转、刷新，以及代表错误调用输出到文件还是终端。使用的 logger 类型决定同步或异步。把控制台启动提示、交互命令和系统关闭事件的实际入口分别追到结果。 |
| 线程和调度 | 从注册或启动处列出实际入口、工作内容、触发周期/配置、等待或退出方式。区分框架回调线程、应用 worker、定时器和派生线程。核对 join、detach、停止信号及共享资源的释放关系。注释和未被启动的函数不计作运行职责。 |
| 配置加载与热更新 | 对代表配置追“触发 → 路径/默认值 → 解析/校验 → 发布与同步 → 读者 → 失败后状态”。区分启动加载、手工重载、自动监听/轮询、按需加载和仅清缓存。多文件重载逐项核对返回值、是否允许部分生效及读者能否看到新状态。配置能被重新解析不代表已建立运行时入口。 |
| 业务到文件 | 从请求、命令、定时任务或回调找到真实分发，再定位声明、实现、状态与存储、响应/通知。回查大文件、头文件与同名模块是否混合多种职责。用“业务 → 入口 → 实际文件与符号 → 状态/依赖 → 输出”记录代表路径；共用文件可归入多个职责。 |

以代表链路建立覆盖，再记录没有对应实现或尚未追到的项。结论应能区分“源码有实现”“在指定启动路径或条件下启用”“效果已运行验证”。评估框架提炼时，把这些已经查实的职责加入原到目标的映射。协议使用占位时，仍需交代相关运行能力和文件职责的保留、合并或排除。

## 配置文件风格与契约

分析配置写法或修改配置时，选目标文件与同模块代表样本，沿实际调用核对文件路径、模板或部署副本、加载器和读取方。若配置由工具生成，先确认源模板和生成入口。记录配置结构或脱敏例子，避免输出实际密码、令牌或私钥。

- **文件写法**：核对文件命名和扩展名、键名大小写、分组与层级、键顺序、缩进、列表写法、引号、空行与注释。注释中的单位、取值和缺省说明要和加载器对照。同一项目可能混用键名和组织方式，新增字段沿用所在文件及同组字段的惯例。
- **解析契约**：按具体键路径核对类型、必填或可选、缺失/空值/错误类型、默认值来源、范围、版本和未知键处理。标明配置示例里的值和程序缺省值。定位读取代码后再判断能否重命名、移动层级或去掉引号。注释或相邻文件的 `version` 字段不足以证明本加载器检查版本。
- **来源与生效**：有多来源时核对配置文件、环境变量、启动参数等实际覆盖顺序。核对读者何时取得值，以及重载成功、失败后读到旧值、默认值还是部分更新。
- **验证**：只改排版时，对照改前改后解析值，检查注释和局部样式。有键、类型或默认值变化时，用现有加载器或验证器检查与本次改动有关的有效、缺失或错误样本。区分文件能解析、加载器接受、消费者实际生效。

## 区分四种容易混淆的现象

- **代码存在与实际启用**：实现和构建项存在，不等于运行会启动；注释掉的调用、条件编译和配置分支要单独标注。
- **规范与偶然写法**：明确配置/文档、模块稳定惯例、历史例外、缺陷分别记录。不要用一处写法推断全项目风格。
- **架构与代码坏味道**：全局状态、跨模块访问等可能是当前架构事实；可以提出改进，但不能先改掉再宣称原架构如此。
- **名称与真实职责**：名为缓存的模块可能承载存储适配，头文件可能装载业务数据。以实际分支和调用链判断，不按名称自动分层。

## 分析结果应能支持实现决定

按任务需要将结果收敛到回复、既有文档或一份简短分析档案。只保留影响当前任务的主题，全项目分析应覆盖主要职责：

| 内容 | 应能回答的问题 |
| --- | --- |
| 职责与依赖 | 哪些模块承担核心职责？调用/数据依赖指向哪里？哪些只是逻辑模块而非独立服务？ |
| 生命周期与关键链路 | 从初始化到功能结果和清理如何串起来？哪些步骤发生在入口之前？ |
| 状态与资源归属 | 谁创建、谁持有、谁更新、谁销毁？锁和回调顺序有什么已证实的保证？ |
| 风格与例外 | 哪些写法应该延续？哪些缺陷需要有意识地偏离？依据是什么？ |
| 未知与影响 | 尚未确认什么？会影响哪个提炼决定？下一步如何确认？ |

框架提炼还需“原职责 → 目标位置 → 保留/合并/模板化/排除 → 理由”的对应表。用户只允许替换具体协议时，不据此默认重划全部模块边界。新架构选择需明确标为本次设计，并解释对需求的必要性。

## 双向源码对照

审查已有提炼或迁移实现时，从两边的当前源码分别追链，再配对结果。核对历史报告和测试记录对应的源码版本、实际使用的 Skill 版本、运行环境和替换依赖。没有提交标识且历史结果会影响当前结论时，用受影响文件的快照或内容哈希核对版本。记录审查是否独立执行。

1. **从参考到目标检查遗漏。** 沿当前入口、启用条件和清理路径核对关键职责。关注参考路径中存在但目标缺失的状态、资源和调用边。业务协议允许占位时，仍须判断会话、持久化、后台任务等框架职责如何承接。
2. **从目标到参考检查新增。** 对目标的服务启动、状态容器、公共入口和依赖找到参考对应。特别检查目标新增的启动前置条件、所有者、跨模块依赖和失败处置。遇到同名文件或类型，先核对谁调用它、它持有什么以及何时执行。构建项、文本包含和运行入口各自核实。
3. **以边界变化定性。** 每条有影响的差异记录两边的符号、实际启用条件、调用者或所有者，以及可观察影响。按本次要求判定为保留、允许的模板替换、有意调整、偏差或待核实。观察到参考问题时可建议偏离，保留理由与当前授权依据。仅有静态路径时写清触发前提，不能当成运行复现。
4. **用反例检验结论。** 至少沿一个不利于“已经对齐”的路径核查，例如停用监听变成必启、同名结构体失去原有身份或成员关系、同一外部故障在不同层变成不同结果。对疑似过度防御，先查其他入口、业务状态变化和锁内复核。既有检查已覆盖原则却漏报时，补验证步骤或输入，避免重复堆规则。

对照结果按影响排序。每条结论应能回答“源端证据、目标证据、实际后果、现有验证是否覆盖”。仅审查一个模块时，只跟踪与该模块相连的边界。

## 分析何时足够

可以解释目标行为由哪些实现和条件产生，识别相关消费者/状态归属，说明未知是否影响结论，并选出能区分正确与错误的验证方法时，当前范围的分析即足够。若用户只要求分析，此时交付分析结果；明确要求修改时，才进入实现。

对影响当前决定的未知继续调查；无关未知写明范围即可，不阻塞工作。不要求读完所有文件、不以凑齐表格为完成条件。仅在缺少的事实无法从项目取得且会影响关键范围或契约时询问用户，不增加例行审批。

若工作被中断，区分“已经确认的结论”和“未完成的分析”。不要把部分阅读称为全项目学习完成；也不要把尚未验证的新框架当成已验证的提炼结果。
