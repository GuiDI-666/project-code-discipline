# 代码示例与取舍

以下是决策示例，不规定项目必须使用 TypeScript 或某种异常类。修改前先核对所在项目契约。

## 1. 校验放在边界

条件：HTTP 入口已用项目 schema 校验，`Order` 的必填字段是可信内部契约，调用链不会在中途破坏它。

```ts
// 多余防御：把内部契约破坏伪装成合法金额。
function total(order?: Order): number {
  if (!order || !Array.isArray(order.lines)) return 0;
  return order.lines.reduce((sum, line) => sum + (line?.amount ?? 0), 0);
}

// 沿用入口校验后的契约。
function total(order: Order): number {
  return order.lines.reduce((sum, line) => sum + line.amount, 0);
}
```

若实际传入的是 `JSON.parse` 得到的未知对象、旧数据库数据或公共库调用参数，上述前提不成立：在边界使用项目 schema 校验后再调用内部计算。金额范围、精度等业务校验仍按契约处理。不要直接用 `as Order` 替代校验。

## 2. 不把故障伪装成“没有数据”

```ts
// 若契约要求区分查询失败与查询为空，此处会掩盖数据库故障。
async function listOrders(): Promise<Order[]> {
  try {
    return await repository.listOrders();
  } catch {
    return [];
  }
}

// 让项目已有的上层错误边界负责转换和记录错误。
async function listOrders(): Promise<Order[]> {
  return repository.listOrders();
}
```

如果产品明确要求离线显示缓存，则可以降级到已定义的缓存结果，并保留项目要求的过期标记或错误信号。逐项导入允许部分成功时，可捕获单项错误并返回明确的成功/失败结果。是否允许降级由契约决定，不由代码行数决定。

## 3. 重试需要副作用语义

查询被限流时，可复用现有客户端的有限重试策略。付款请求超时可能表示“已扣款但响应丢失”，直接重试可能重复扣款；应按现有幂等协议或查询结果处理。若上层已经重试，不在底层再叠一套。不可重试的参数错误应及时返回。

## 4. 抽象要解决当前职责

一个有清晰职责的函数即使只有一次调用，也可能值得提取；不因“一次调用”禁止它。为了假想中将来的第二种存储，先创建工厂、注册中心和适配器则需要当前需求支持。优先沿用项目已存在且语义匹配的接口。

## 5. 风格有局部性

若支付模块稳定使用 `Result`，新代码通常延续它，不因为另一个模块抛异常就改写支付模块。但如果项目已明确迁移到统一错误机制，按迁移范围执行。旧代码直接拼 SQL 时不应继续复制漏洞；使用项目现有参数化查询，并说明与旧写法的必要差异。

## 6. 回归测试验证行为

修复“库存不足仍创建订单”时，验证返回契约及没有创建订单/扣减库存等副作用。只验证新加的 `if` 存在或 mock 返回了预设值，不能证明修复。若测试原断言确实反映旧契约，不能为了当前实现方便而删除它。

## 7. 看似重复的检查可能有不同保证

入口先判断“是否已绑定”，避免不必要的数据库查询；查询返回后在共享状态锁内再次判断，以防期间另一项任务已完成绑定。前者是快筛，后者保证状态转换，不能仅因为条件相似就删掉锁内检查。先核对项目是否真的允许这种交错；完全同步且独占的调用链也不能凭空要求复核。

审查报告应指出检查的对象、保证来源和重复关系。无法证明重复时标为分析疑点，不能直接给出“删除判空”之类的修复建议。

## 8. 先命名问题，再选择修改

固定写出几个字节却分配很大的临时缓冲，首先是内存或分配成本问题，不能仅凭“预留很多”就归类为过度防御。先确认写入上限、传给发送函数的实际长度和指针递增方式，再考虑缩小缓冲；可变长度编码器不能照搬固定长度结论。

作用域包装器保证归还资源，不一定保证成功取得资源。如果其构造器会捕获异常或获取函数可返回空指针，使用点的失败检查仍然必要。评价某个检查时，保证来源应是项目实际契约，而不是“RAII”“强类型”等模式名称。

## 9. 复用与辅助函数

例如给现有协议添加字段。先查相邻回包的写入调用，并到字节工具定义确认写入宽度、字节序、游标推进与可写容量。如果已有对应函数，直接调用该函数。只转发原调用的本地别名或另写一套编码会增加维护点。

相反，同名函数若处理不同的长度含义、鉴权、事务或资源所有权，先确认调用边界。不要为复用而绕开校验，也不要仅因多个模块都有同名函数就扩大其可见性。原入口可以兼容地承担新增能力时，把扩展放回原职责所在模块。若确实缺少匹配行为，按当前需求保留最小局部实现，并说明为什么现有入口不匹配。审查新增符号时检查最终调用方和是否留下平行实现。

## 10. 排查与验证取舍

- **多次尝试后的补丁**：回看最终差异与当前证据。已排除的假设若留下新配置、日志、兼容分支、包装器或测试改动，去掉本次引入的残留，再验证受影响路径。工作树有用户修改时，以本次编辑记录或原始差异辨明归属。
- **验证对象**：生产调用函数 A，自检调用测试目录中的同名实现 B，测试通过仅覆盖 B。让检查走生产入口或同一份实现。命令启动了旧二进制、错误工作目录或另一个服务时，也只能报告实际测到的对象。涉及新增依赖或交付环境时，核对声明、锁定版本、运行资源与启动命令。按任务风险选择干净环境验证。
- **部分成功和失败**：追踪操作何时提交、提交前能回滚什么、提交后哪些步骤还能失败。例如文件已经写入且备份已删除，此后写诊断日志失败，用户看到的结果应反映文件已更新。重试前先确认是否会重复提交或留下第二份资源。根据项目契约决定日志、通知或重启失败是否单独报告。
- **风格整理**：核对输出、错误、顺序和副作用是否仍符合原契约。判断某个防御分支是否可删时，明确它保护的输入和保证来源。检查覆盖一条路径或行数下降都不足以证明分支多余。
- **顺序改变**：把逐项解析并执行改成先解析整批，需比较“前项有效、后项失败”的输入。两者可能都报同一错误，但前项的输出或副作用不同。对流式入口固定回调/分块边界，不用两次网络写入假定会产生两次接收；按相关契约决定差异是否允许，不默认要求事务化或自动回滚。
