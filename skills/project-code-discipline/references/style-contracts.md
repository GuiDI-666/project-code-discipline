# 定义与使用风格复原

用于学习项目后按原项目约束编程，或用户要求通过复原样本验证 Skill。复原指能准确重现源项目的定义、命名、位置和使用习惯，不是设计一个职责类似的新实现。

## 先说明复原范围

选定需要验证的代表符号和调用链，记录实际源码及条件分支。样本应覆盖用户强调的维度；不以复制整个项目增加规模。用户指定可编辑样本时，在该样本实际改码；未指定时可在当前工作区测试目录生成样本。参考项目只读。

“保留原定义”“生成同风格新代码”“提出架构改进”是不同任务。先按用户目标选择，不能把后两者当作第一项的结果。允许模板业务体不等于允许更改接口、字段或文件归属。

## 建立可以核对的符号契约

| 维度 | 需要从源码取得的内容 | 常见误差 |
| --- | --- | --- |
| 类型定义 | 类型类别、字段名、字段类型、可见性、默认值，以及语言或消费者依赖的布局 | 保留类型名但替换其字段、把有序集合改为无序集合 |
| 函数定义 | 所属模块、名称、参数、默认值、返回值和语言适用的限定符 | 丢掉可选参数、把同步接口改为异步、改变错误类型 |
| 文件归属 | 定义、声明、导出和注册位置，以及真实依赖方向 | 把内部函数移到公共模块，或将业务逻辑移入入口 |
| 调用方式 | 真实调用方、实参来源与顺序、辅助函数、状态、副作用与资源释放 | 只复原签名却使用新包装器、改变持有方式、按名称猜调用顺序 |
| 命名与排版 | 所在模块的大小写、前后缀、类型别名、括号/空行、参数换行、声明分组、注释位置 | 套通用格式后宣布学会原风格，压缩函数/枚举/多个语句 |

契约条目应指向实际符号和文件范围，列出适用配置以及尚未找到的部分。条件编译会影响字段或签名时一并记录；不能任意选择分支后声称覆盖全部版本。语言不使用头/源文件分离时，记录其实际模块和导出/使用位置。

## 沿值和调用追到使用点

对需要沿用的关键路径，记录值从哪个入口取得、何时验证或转换、传给谁、谁持有或修改状态，以及结果或错误由谁消费。比如命令行工具应核对参数默认值、处理函数、stdout/stderr 与退出码。组件项目应核对事件、状态所有者和渲染更新。

### 二进制协议示例

只有涉及二进制数据和相关分发时，才检查以下细节：

- 值来自哪个字段、如何转换字节序、用什么局部类型和名称保存，再作为第几个实参传给谁。
- 接收方参数是否按值、指针、引用或输出参数传递；switch 使用原始消息号、枚举还是其他值，case 是具体数字、宏还是枚举项。
- 指针是持有者、借用者还是缓冲区内部地址；辅助函数是否通过 `BYTE*&` 等形式推进游标，推进影响调用者还是仅影响当前函数的局部副本。
- 长度描述原始缓冲、协议声明长度还是当前剩余长度；是否包含头字段或保留部分。证据不足时保留原用法并标注未知，不擅自“统一”长度。
- 内存由谁分配和释放，调用返回后地址是否继续有效；不要把同步借用改成保存到新对象，也不要用新的容器/包装器替换后宣称保持原使用方式。

把这条使用链写成带类型与实参的短记录，而不是仅列函数名。例如，若源码是 `USHORT MsgID`、`BYTE* Body`、`switch (MsgID)`、`case 100`，复原不能自行改为消息对象、`static_cast<MsgID>` 和枚举 case。这里的变量 MsgID 是数值；不能因为同条链路使用 Body 指针就把消息号本身也描述成指针。具体类型与分发风格从目标项目取得，此例不是所有项目的通用写法。

### 编解码与响应构造

不能把“最后都能得到一组字节”视为相同使用风格。对于二进制协议或相似的数据处理代码，核对：

- 业务处理函数如何取得缓冲区、游标如何初始化，Read/Write 辅助函数的参数是容器、原始指针还是指针引用，实际长度如何计算。
- 函数是返回值对象、修改输出参数还是直接发送；调用方继续使用哪些值，缓冲区在同步调用结束后能否释放。
- 业务响应构造、消息头/外层头封装、加密、路由与网络发送各属于哪一层，不用一个新通用编码器替换这些层的实际接口。
- 消息编号、类型、序号、字节序和长度字段从哪里取得；不能根据常见做法自创应答位、状态码、帧布局或自动转换。
- 失败路径是 BOOL/错误码返回、上层转译还是异常；检查的边界与失败语义要一起记录，不能只模仿一个长度上限。

例如，若同模块的响应函数使用 `std::vector<BYTE> buf`、`BYTE* p = buf.data()`、`Write32(p, value)`、`len = p - buf.data()`、`SendToClient(Client, MsgID, ..., len, 路由参数, Response)`，同风格样本应保留这条调用模式。自行改成 `Bytes EncodeResponse(const Message&, Status, const Bytes&)`、`out.insert`、返回新容器或 `id | 0x8000`，需要明确的新设计任务支持，不能用“更现代”或“模板协议”解释为复原成功。

此例不要求复制不合理的大缓冲或删除必要边界检查。评估时先判定其是否忠实复原；性能、安全与架构建议单列，不能边“优化”边改变正在检验的契约。

已有样本的协议与参考不同、而用户只要求改写法时，先分清两套契约：参考决定分工、定义位置和调用形态；样本决定仍须保留的字段编码、消息值、成功与失败语义。模板特有字段留在对应层（例如应答位只留在模板封帧层），不加参考项目独有的路由或加密参数来凑签名。记录因此不能精确复原的项。精确复原任务若确实要求替换这些契约，则按授权范围变更并核对消费者。

对于要求精确复原的已有定义，保留适用的类型拼写、字段顺序和参数名称。若任务明确允许裁剪，给出保留与排除清单，标明同名定义的差异。

## 复原与改进分开判断

原项目可能混用风格，甚至把实现写进头文件或 include 一个 .cpp。这是复原时需要记录的事实，不代表值得推广。未获架构修改任务时，不因个人偏好改变其声明/定义归属；发现问题可单独提出建议。

复原声明和字段并不要求执行有问题的实现。涉及缺陷时，保留接口证据，单独说明实现风险与建议；不能以“优化”为由悄悄改变本次要验证的契约。

新代码应找到目标模块中职责相近的声明、定义与调用样本，再沿用其模式。没有对应样本的新增设计明确标为新增，不能冒充复原结果。无需把整个模块历史写法全部统一。

## 验收分为互不替代的检查

1. **定义复原**：对照完整类型与函数契约，检查字段、类型、顺序、默认值、参数、限定符等。必要时比较语法 token 或 AST；单纯忽略空白的比较不能检查排版，不能漏掉条件编译或 pack 上下文。
2. **位置与调用复原**：核对声明、定义和调用文件，确认调用顺序、参数、值转换、指针推进与资源使用方式；同样的签名出现在错误文件或以错误方式调用，也属于失败。
3. **风格复原**：与选定的局部样本比对命名、换行、声明分组、初始化和辅助函数用法。有现成配置就执行；没有配置先记录观察依据，不能机械套一个预设。禁止用短行数或编译通过代替可读性检查。

核对换行时，分别观察独立语句、一个完整语句内部和控制块。如果同类参考调用或签名通常在一行，保留能读清的完整行，避免把每个参数拆成一行。复杂条件和带回调体的调用可在有意义的分组处续行。函数和控制块仍按项目的大括号与缩进规则排版。对有意调整 formatter 的任务，先用代表性的声明、调用和块检查输出，确认合并语句内部换行后仍保留块和独立语句的边界。未经授权的配置冲突只记录。

评估检查方法时，加入可区分的错误样本，例如改一个字段类型、调换参数、改变定义文件或压缩排版，确认它们会被指出。把已有不符合要求的样本作为反例，不能只验证原文复制的正例。

直接提取的源码片段可以证明记录与比较工具准确，但不能单独证明 Skill 能指导代码修改。评估时保留改前快照或基线，选取一条用户关注的完整路径实际改写，覆盖受影响的声明、定义和消费点。将差异与参考链逐项对照，同时复用或补充能观察原行为的检查，尽可能对同一组输入比较改前与改后结果。涉及编码、发送或错误返回时，比较实际字节或调用结果；只搜索新旧关键词、构建通过或运行基线正例不能替代这一步。

记录哪些项精确复原、哪些仅沿用形态、哪些未覆盖，并区分同一执行者的实作与独立评估。验收失败时，记录具体差异及对应的 Skill 决策缺口，修订后重验受影响的项；不要用增加样本功能替代改进 Skill。
