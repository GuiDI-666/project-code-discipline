# 从现有项目提炼最小框架

仅在用户明确要求实际提炼框架或迁移架构时使用。单纯学习项目、审查架构或评估 Skill 不进入实现。目标是保留必要职责和运行链路，具体业务或协议可按用户范围替换；“最小”不等于只有几个能编译的空类。

## 提炼前留下可核对的依据

先完成 [项目分析与证据](project-analysis.md) 中与保留范围有关的分析，复用其结论，不重复生成一套文档。补充“原职责 → 目标位置 → 保留/合并/模板化/排除 → 理由”的对应表，检查排除理由是否符合用户范围。资料不全时标注待核实项，不能宣布已经完成全项目学习。

默认以有证据的原职责和依赖关系作为提炼起点。用户允许模板协议，不代表允许不加说明地重写模块架构。调整职责、合并模块或更换状态模型时，在对应表中说明哪些属于新设计及其必要性；不能仅因新方案更熟悉而替换。

对跨模块职责，在两边分别取得以下证据，再配对；只填写影响本次范围的维度，不要求每个符号都建表：

| 对照维度 | 需要核实的边界 |
| --- | --- |
| 构建与归属 | 实际编译项、文本包含/导入、声明和定义位置；同名文件或类的实际职责 |
| 启用与阶段 | 触发条件、启动前置条件、初始化/回调/关闭阶段；禁用能力是否成为目标的硬依赖 |
| 状态与资源 | 创建、持有、身份索引、读写与销毁；聚合对象是否合并了原本独立的状态 |
| 顺序与提交 | 解析、校验、交付、副作用及提交的先后；逐项处理是否改为整批处理 |
| 失败与结束 | 实际返回值及调用者处置、部分成功、回滚和取消后的状态；停止调用是否保证依赖可以销毁 |

映射同时指向原端和目标端符号，写明差异属于允许替换、有意调整还是偏差，以及现有验证是否覆盖。实现后按 [双向源码对照](project-analysis.md#双向源码对照) 复查，再用构建和运行验证各自能证明的内容。

完整基础框架的映射包含已查实且与交付范围有关的 [运行能力与业务分布](project-analysis.md#运行能力与业务分布)。例如，日志能写文件只证明一个输出端，不能代替崩溃转储或控制台命令。保留配置读取接口时，另核对运行时重载入口、发布方式与失败行为。对原先分布在多个文件的业务保留其职责说明，合并实现时记录实际归宿和影响。

## 限定模板职责

按项目的真实入口设计最小示例，例如一条命令、一次界面交互、一项库调用或一条服务请求。记录示例替换了哪些业务行为或外部依赖，以及保留了哪些职责。新增的状态模型、数据格式或依赖须有当前用途。

检查实际依赖方向和用户要求保留的边界。发现共享数据结构引入了额外数据库或网络依赖时，说明引用链与影响。仅当本次允许调整且有实际收益时，采用窄头文件等最小改动；不把偏好的分层方式当成原架构，也不为解耦新增接口工厂层。

## 对真实边界检查关键不变量

按本次保留模块选择相关项，不要求逐项实现额外机制：

| 模块 | 要明确并验证的契约 |
| --- | --- |
| 输入与输出 | 按实际入口核对参数、文件、事件或请求的校验及错误结果。流式或批量处理核对分帧、缓冲与交付时机，按需比较同批和分批输入 |
| 状态转换 | 状态归属、允许的转换、失败或取消后的状态一致性 |
| 定时任务 | 快照与执行之间状态可能变化时，过期判断是否仍有效；取消与关闭是否等待工作结束 |
| 数据库与资源池 | 获取失败、等待超时、连接失效和业务未命中分别如何上报；失败连接是否再次流入池中 |
| 启动与关闭 | 部分初始化失败如何释放已取得资源；停止是否等待回调结束后再销毁其依赖 |

依据库文档、源码或运行证据决定是否需要连接替换、额外锁或重试。不要仅因表格提及就添加一套自动恢复框架。发现缺口时明确当前限制，按任务要求解决。

## 验收基于最终产物

对于可运行的框架，用项目现有工具验证最终产物，经实际入口跑一条代表流程，并按保留的核心职责选择必要失败路径。编译型项目记录构建结果，其他项目采用适用的检查或运行方式。只有交付声称真实网络或数据库链路可用时，才验证相应的真实依赖。采用夹具时说明实际覆盖范围。

检查持久文档、AGENTS 引用和实际文件是否一致。明确尚未运行的部分及其原因。中断导致的未完成工作属于待办，不自行当成最终方案缺陷；但也不能把中断前的部分成功当成整体通过。
